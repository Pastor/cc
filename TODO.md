# Требования

Спецификация предметной области `cstorage` — криптографического файлового
хранилища. Документ является источником требований: при расхождении с кодом или
с [CLAUDE.md](CLAUDE.md) прав он.

Правила процесса — в [CLAUDE.md](CLAUDE.md), правила написания кода — в
[RULE.md](RULE.md), текущие задачи — в [TASKS.md](TASKS.md).

---

## 1. Модель безопасности

### 1.1 Выбранная модель

Гибридная схема: **ключи выводятся и применяются на клиенте, сервер хранит
только шифротекст и обёрнутые ключи**. Сервер не располагает материалом,
достаточным для расшифровки содержимого, ни в покое, ни во время работы.

Пароль пользователя **никогда не передаётся на сервер**. Из пароля на клиенте
выводится мастер-ключ, из него двумя независимыми ветвями — ключ шифрования
(остаётся на клиенте) и аутентификационный хеш (уходит на сервер вместо пароля).
Знание аутентификационного хеша не позволяет вывести ключ шифрования.

Схема соответствует общепринятой практике хранилищ секретов и файлов; ближайший
описанный аналог — Bitwarden
(<https://bitwarden.com/help/bitwarden-security-white-paper/>). Смежные модели:
Cryptomator (<https://docs.cryptomator.org/security/architecture/>) и Proton
Drive (<https://proton.me/blog/protondrive-security>).

### 1.2 Ключевая иерархия

```
пароль
  └─ Argon2id(пароль, соль_пользователя)            → мастер-ключ        [клиент]
       ├─ HKDF(мастер-ключ, "auth")                 → аутентификационный хеш  → сервер
       └─ HKDF(мастер-ключ, "enc")                  → ключ шифрования    [клиент]
                                                       │
случайный ключ учётной записи (256 бит)  ←── оборачивается ключом шифрования
  ├─ оборачивает закрытый ключ пользователя
  ├─ оборачивает имена файлов и директорий
  └─ дополнительно оборачивается ключом восстановления

пара ключей пользователя (открытый / закрытый)
  └─ открытый ключ хранится на сервере открытым, используется для выдачи доступа

случайный ключ содержимого (256 бит, свой у каждого файла)
  ├─ шифрует содержимое файла (AEAD, на клиенте)
  └─ оборачивается открытым ключом каждого, кому выдан доступ

случайный ключ метаданных файла (256 бит, свой у каждого файла)
  ├─ шифрует публичную метаинформацию файла, включая имя
  └─ оборачивается вместе с ключом содержимого при выдаче доступа

ключ тегов = HKDF(ключ учётной записи, "tags")
  └─ детерминированные метки тегов для группировки на сервере
```

**Ключ метаданных отделён от ключа содержимого намеренно.** Он позволяет выдать
получателю право видеть имя и описание файла, не выдавая права читать
содержимое, а также обновлять метаданные, не трогая шифротекст.

Промежуточный **ключ учётной записи** обязателен: он делает смену пароля
дешёвой. При смене пароля перешифровывается только он, а закрытый ключ, имена и
все ключи содержимого остаются нетронутыми.

Аутентификационный хеш на сервере хранится не как есть, а как
`Argon2id(аутентификационный хеш, серверная соль)`: утечка базы не должна давать
возможность войти.

### 1.3 Модель угроз

| Противник | Возможности | Защищено |
| --- | --- | --- |
| Внешний злоумышленник без доступа | Сеть, публичные интерфейсы | Да: TLS, аутентификация, ограничение частоты |
| Другой пользователь сервиса | Валидная учётная запись и сессия | Да: доступ только к своим файлам и выданным ссылкам |
| Похититель носителя или резервной копии | Полный доступ к данным в покое | Да: содержимое, закрытые ключи и имена файлов зашифрованы |
| Администратор сервера, пассивный | Полный доступ к базе, диску, логам | Да для содержимого, имён и ключей. Нет для метаданных: размеры, время, граф доступа |
| Администратор сервера, активный | Может подменить код, отдаваемый клиенту | **Нет.** Веб-клиент доставляется сервером; подменённый клиент способен похитить пароль |
| Активный сетевой посредник | Перехват и подмена трафика | Да: TLS 1.3, HSTS |
| Получатель, которому выдали доступ | Знает ключ содержимого | **Нет и не может быть защищено:** отзыв доступа не отменяет знания ключа |

Две последние строки — принципиальные ограничения, а не недоработки. Их нельзя
устранить в рамках выбранной архитектуры, и обещать обратное запрещено.

### 1.4 Что сервису видно

Сервер **не видит**: паролей, мастер-ключей, ключей шифрования, закрытых ключей,
ключей содержимого, ключей метаданных, содержимого файлов, имён файлов и
директорий, закрытой и публичной метаинформации, значений тегов.

Сервер **видит**: идентификаторы пользователей и их почту, открытые ключи,
техническую метаинформацию (размеры, хеши шифротекста, время, версии формата),
структуру дерева директорий по идентификаторам, детерминированные метки тегов,
структуру связей «кто кому выдал доступ», адреса и сведения о клиентах в журнале.

Утечка размеров и графа доступа принята осознанно: их сокрытие требует
паддинга и слепых протоколов, что несоразмерно задаче.

### 1.5 Ограничения

- Пароль на сервер не передаётся ни в каком виде.
- Ключи шифрования наружу от клиента не передаются.
- Ключ содержимого в открытом виде существует только в памяти клиента.
- Файл шифруется на клиенте; на сервер уходит только шифротекст.
- Ключ содержимого оборачивается открытым ключом получателя и хранится на
  сервере обёрнутым.
- Транспорт — только TLS 1.3, с HSTS.
- Все авторизованные вызовы несут сессионный токен.
- API не имеет метода, отдающего ключ шифрования, закрытый ключ или ключ
  содержимого в открытом виде — их у сервера нет.
- Забытый пароль без ключа восстановления означает безвозвратную потерю доступа
  к файлам. Пользователь предупреждается об этом при регистрации.

## 2. Криптографические примитивы

Алгоритмы фиксируются здесь и не выбираются реализацией самостоятельно.

| Назначение | Алгоритм | Норматив |
| --- | --- | --- |
| Выведение ключа из пароля | Argon2id | <https://www.rfc-editor.org/rfc/rfc9106> |
| Разделение мастер-ключа на ветви | HKDF-SHA-256 | <https://www.rfc-editor.org/rfc/rfc5869> |
| Шифрование содержимого и имён | XChaCha20-Poly1305 либо AES-256-GCM | <https://www.rfc-editor.org/rfc/rfc8439>, <https://csrc.nist.gov/pubs/sp/800/38/d/final> |
| Обёртывание ключей | X25519 + HKDF | <https://www.rfc-editor.org/rfc/rfc7748> |
| Хеш шифротекста | SHA-256 | — |
| Транспорт | TLS 1.3 | — |

Требования:

- Параметры Argon2id подбираются измерением и хранятся вместе с пользователем,
  чтобы их можно было усилить, не ломая существующие учётные записи. Нижняя
  граница — рекомендации OWASP:
  <https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html>
- Соль уникальна на пользователя и генерируется криптографическим ГПСЧ.
- Шифрование только аутентифицированное (AEAD). Режимы без аутентификации
  запрещены.
- Nonce уникален для каждой операции. При AES-GCM с 96-битным nonce — счётчик
  либо смена ключа; при XChaCha20 допустим случайный.
- Все сравнения секретов — в постоянном времени.
- Ключи в памяти затираются после использования.
- Общие требования: <https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html>

**Хеш содержимого считается от шифротекста, а не от открытого текста.** Хеш
открытого текста позволил бы подтвердить наличие известного файла у
пользователя. Как следствие — дедупликация содержимого между пользователями
невозможна и не предусматривается.

## 3. Модель данных

Отметка `[x]` означает, что сущность реализована.

- [ ] **Пользователь**
  - Идентификатор
  - Логин (адрес электронной почты)
  - Аутентификационный хеш (хранится как `Argon2id` от него с серверной солью)
  - Соль пользователя и параметры Argon2id
  - Обёрнутый ключ учётной записи
  - Обёрнутый закрытый ключ
  - Открытый ключ (в открытом виде)
  - Время подтверждения почты
  - Время создания, время последнего входа
  - Состояние: активен, заблокирован, ожидает подтверждения

- [ ] **Ключ восстановления**
  - Пользователь
  - Ключ учётной записи, обёрнутый ключом восстановления
  - Время создания, время использования
  - Отпечаток для сверки (не сам ключ)

- [ ] **Внешняя личность**
  - Пользователь
  - Провайдер: `vk`, `telegram`
  - Идентификатор у провайдера
  - Время привязки, время последнего входа
  - Уникальность по паре «провайдер + идентификатор»

- [ ] **Сессия**
  - Идентификатор
  - Пользователь
  - Хеш токена (сам токен не хранится)
  - Набор разрешённых действий
  - Время создания, время истечения, время последнего обращения
  - Сведения о клиенте: адрес, `User-Agent`
  - Признак «ключи развёрнуты»: сессия, созданная внешним входом без ввода
    пароля, доступа к зашифрованным данным не даёт

- [ ] **Профиль**
  - Пользователь
  - Отображаемое имя
  - Дополнительные имена (опционально, без жёсткой структуры)
  - Аватар (изображение, хранимое локально, либо генерируемое по
    идентификатору; обращения к внешним сервисам запрещены)
  - Телефон (опционально)
  - Время подтверждения телефона
  - Профиль квот

- [ ] **Подтверждение**
  - Тип: почта, телефон
  - Пользователь
  - Одноразовый код (хранится хешем)
  - Время создания, время истечения, число попыток

- [ ] **Дисковая квота**
  - Имя
  - Максимальный размер в байтах

- [ ] **Профиль квот**
  - Имя
  - Дисковая квота

- [ ] **Содержимое**
  - Идентификатор
  - Владелец
  - Размер шифротекста
  - SHA-256 шифротекста
  - Время создания
  - Путь в хранилище, выводимый из идентификатора, а не из хеша

- [ ] **Директория**
  - Идентификатор
  - Владелец
  - Родительская директория (пусто для корня)
  - Зашифрованное имя
  - Время создания, время изменения

- [ ] **Файл**
  - Идентификатор
  - Владелец
  - Директория
  - Содержимое
  - Техническая метаинформация (открыта серверу)
  - Зашифрованная публичная метаинформация, включая имя
  - Зашифрованная закрытая метаинформация
  - Права владельца: чтение, запись, удаление, выдача доступа, публикация

- [ ] **Метаинформация файла**

  Три категории с разной видимостью и разными ключами:

  | Категория | Кому видна | Чем защищена | Состав |
  | --- | --- | --- | --- |
  | Техническая | Серверу и всем, у кого есть доступ | Не шифруется | Размер шифротекста, SHA-256 шифротекста, версия формата шифрования, время создания и изменения, идентификаторы связей |
  | Публичная | Владельцу и всем, кому выдан доступ | Ключ метаданных файла | Имя, расширение, тип содержимого, описание, размер открытого текста, произвольные пары «ключ-значение» от владельца |
  | Закрытая | Только владельцу | Ключ учётной записи | Личные заметки, теги, метки, любые сведения, не подлежащие передаче вместе с правами |

  Требования:
  - Категория задаётся при записи и не меняется молча: перевод сведения из
    закрытой категории в публичную — явная операция, требующая перешифрования.
  - Техническая категория заполняется сервером и клиентом не переопределяется.
  - Публичная метаинформация передаётся вместе с правами: получатель
    разворачивает ключ метаданных так же, как ключ содержимого.
  - Закрытая метаинформация при выдаче доступа не передаётся никогда и
    получателю недоступна даже теоретически — она зашифрована ключом, которого у
    него нет.
  - Размер открытого текста относится к публичной категории: серверу он не
    сообщается, чтобы не сужать оценку содержимого.

- [ ] **Тег**
  - Владелец
  - Зашифрованное значение (ключ учётной записи)
  - Детерминированная метка: `HMAC(ключ тегов, нормализованное значение)`
  - Время создания

- [ ] **Тег файла**
  - Файл
  - Тег
  - Время присвоения
  - Уникальность по паре «файл + тег»

- [ ] **Ключ доступа**
  - Файл
  - Субъект: пользователь либо ссылка
  - Ключ содержимого, обёрнутый открытым ключом субъекта — присутствует, только
    если выдано право читать содержимое
  - Ключ метаданных, обёрнутый открытым ключом субъекта — присутствует всегда,
    иначе получатель не увидит даже имени файла
  - Кем выдан, когда выдан

- [ ] **Ссылка**
  - Идентификатор
  - Файл
  - Тип: адресная (конкретному пользователю), закрытая (по секрету в ссылке),
    публичная (доступна всем, кто знает адрес)
  - Права: чтение, скачивание, повторная выдача
  - Получатель — для адресной ссылки
  - Срок действия, ограничение числа обращений
  - Время создания, время отзыва

- [ ] **Запись журнала**
  - Пользователь, сессия
  - Действие, объект, результат
  - Время, адрес, сведения о клиенте

Решение по прежней развилке: **одно содержимое — один ключ**. При выдаче доступа
ключ содержимого перешифровывается под получателя и хранится как отдельная
запись «Ключ доступа». Вариант «свой ключ каждому пользователю»
отклонён: он требует хранить копию шифротекста на каждого и делает выдачу
доступа операцией, пропорциональной размеру файла.

## 4. Описание работы

### 4.1 Регистрация

1. Клиент запрашивает параметры Argon2id, принятые сервисом.
2. Клиент генерирует соль, выводит мастер-ключ, из него — ключ шифрования и
   аутентификационный хеш.
3. Клиент генерирует ключ учётной записи и пару ключей, оборачивает ключ
   учётной записи ключом шифрования, закрытый ключ — ключом учётной записи.
4. Клиент генерирует ключ восстановления, оборачивает им ключ учётной записи и
   **показывает ключ восстановления пользователю ровно один раз**, с
   предупреждением о невосстановимости доступа без него.
5. Клиент отправляет: логин, соль, параметры, аутентификационный хеш, открытый
   ключ, обёрнутый ключ учётной записи, обёрнутый закрытый ключ, обёрнутый
   ключом восстановления ключ учётной записи.
6. Сервер проверяет уникальность логина, сохраняет, отправляет подтверждение на
   почту. До подтверждения учётная запись ограничена.
7. Отказы: логин занят — конфликт; требования к паролю проверяются на клиенте,
   сервер их проверить не может и не пытается.

### 4.2 Вход по паролю

1. Клиент запрашивает соль и параметры Argon2id по логину. Для неизвестного
   логина сервер возвращает **правдоподобные детерминированные** параметры,
   выведенные из логина и серверного секрета, — иначе метод становится оракулом
   существования учётной записи.
2. Клиент выводит мастер-ключ, ключ шифрования и аутентификационный хеш.
3. Клиент отправляет логин и аутентификационный хеш.
4. Сервер сверяет с хранимым значением в постоянном времени, создаёт сессию,
   возвращает токен, срок действия, обёрнутый ключ учётной записи и обёрнутый
   закрытый ключ.
5. Клиент разворачивает ключ учётной записи ключом шифрования, затем закрытый
   ключ. Развёрнутые ключи живут только в памяти клиента.
6. Отказы: неизвестный логин и неверный пароль отвечают одинаково и за
   одинаковое время.

### 4.3 Вход через внешнего провайдера

Поддерживаются VK и Telegram. Протоколы у них разные, и общего слоя OAuth2 для
обоих не существует: у Telegram OAuth2 нет вовсе.

**Учётная запись через внешний вход не создаётся.** Регистрация возможна только
с паролем, потому что без него не из чего вывести мастер-ключ и построить
ключевую иерархию (раздел 1.2). Внешний вход — способ войти в уже существующую
учётную запись, к которой привязана внешняя личность.

Общий порядок:

1. Клиент проходит процедуру провайдера: для VK — OAuth 2.1 с PKCE, для
   Telegram — проверка подписи данных виджета.
2. Сервер проверяет подлинность и находит внешнюю личность.
3. **Автоматическое связывание учётных записей по совпадению почты запрещено.**
   Привязка внешней личности выполняется только из уже аутентифицированной
   сессии. Провайдер, не подтверждающий владение почтой, иначе позволяет
   захватить чужую учётную запись; Telegram почту не отдаёт вовсе.
4. Сессия, созданная внешним входом, имеет признак «ключи не развёрнуты»: она
   даёт доступ к профилю и перечню файлов, но не к содержимому и не к именам.
5. Для доступа к зашифрованным данным пользователь дополнительно вводит пароль
   либо ключ восстановления; сессия повышается до «ключи развёрнуты».
6. Отвязать последний способ входа нельзя.
7. Обратные вызовы провайдеров ограничиваются по частоте наравне с входом по
   паролю: это публичные маршруты.

#### Маршруты

Обмен с провайдером выражается ресурсами, а не глаголами:

| Метод и путь | Смысл |
| --- | --- |
| `POST /api/sessions/authorizations` | создать запрос авторизации у провайдера; ответ `201` + `Location`, тело содержит адрес провайдера |
| `GET /auth/{provider}/callback` | служебный маршрут обратного вызова, вне версионируемого контракта |
| `POST /api/sessions` | создать сессию по завершённому запросу авторизации либо по подписанным данным Telegram |

Запрос авторизации одноразовый, живёт минуты и привязан к клиенту, начавшему
процедуру. Для Telegram первые два шага не нужны: виджет сразу отдаёт
подписанные данные, и клиент передаёт их в `POST /api/sessions`.

#### VK — OAuth 2.1

Документация: <https://id.vk.com/about/business/go/docs> и
<https://dev.vk.com/ru/api/access-token/getting-started>

1. Только authorization code с PKCE (`S256`), RFC 7636:
   <https://www.rfc-editor.org/rfc/rfc7636>. Потоки implicit и по паролю
   запрещены.
2. `state` — случайный, одноразовый, привязанный к запросу авторизации, с
   коротким сроком жизни; ответ без совпадения `state` отвергается.
3. `redirect_uri` сравнивается целиком, посимвольно. Сравнение по префиксу —
   известный способ увести код авторизации.
4. Обмен кода на токен выполняется только сервером; секрет приложения на клиент
   не попадает.
5. Если провайдер выдаёт `id_token`, проверяются подпись, `iss`, `aud`, `exp` и
   `nonce`.
6. Действующие рекомендации по безопасности:
   <https://datatracker.ietf.org/doc/html/draft-ietf-oauth-security-topics>

#### Telegram — подпись данных виджета

Документация: <https://core.telegram.org/widgets/login>, для Mini Apps —
<https://core.telegram.org/bots/webapps>

1. Подлинность проверяется вычислением `HMAC-SHA256` от строки полей,
   отсортированных по имени, с ключом `SHA256(токен бота)`; результат
   сравнивается с полем `hash`.
2. Сравнение выполняется в постоянном времени.
3. `auth_date` проверяется на свежесть: данные старше установленного окна
   отвергаются. Без этой проверки однажды перехваченные данные годятся вечно.
4. Пара «идентификатор пользователя + `auth_date`» запоминается на время окна:
   повторное предъявление тех же данных отвергается.
5. Токен бота — секрет уровня закрытого ключа: только из конфигурации, никогда
   в коде, никогда в журнале.

### 4.4 Смена пароля

1. Пользователь подтверждает текущий пароль обычной процедурой входа.
2. Клиент выводит новый мастер-ключ с **новой солью**, из него — новый ключ
   шифрования и новый аутентификационный хеш.
3. Клиент перешифровывает **только ключ учётной записи**.
4. Клиент отправляет новую соль, параметры, новый аутентификационный хеш и
   новый обёрнутый ключ учётной записи, подтверждая операцию старым
   аутентификационным хешем.
5. Файлы, имена и закрытый ключ не перешифровываются.
6. Все прочие сессии пользователя завершаются.

### 4.5 Восстановление доступа

1. Пользователь вводит ключ восстановления.
2. Клиент разворачивает им ключ учётной записи и далее задаёт новый пароль по
   процедуре смены пароля.
3. Использованный ключ восстановления гасится, выдаётся новый.
4. Без ключа восстановления и без пароля доступ к файлам не восстанавливается
   никакими средствами сервиса. Это следствие модели, а не недоработка.

### 4.6 Загрузка файла

1. Клиент генерирует ключ содержимого, шифрует содержимое потоково, считает
   SHA-256 шифротекста.
2. Клиент генерирует ключ метаданных, шифрует им публичную метаинформацию,
   включая имя и размер открытого текста; закрытую метаинформацию шифрует ключом
   учётной записи.
3. Клиент создаёт файл: директория, техническая метаинформация (размер и хеш
   шифротекста), зашифрованные публичная и закрытая метаинформация, ключ
   содержимого и ключ метаданных, обёрнутые собственным открытым ключом.
4. Сервер проверяет квоту и лимит размера, отвечает идентификатором.
5. Клиент передаёт шифротекст потоком.
6. Сервер сверяет фактический размер и хеш с заявленными; расхождение —
   отклонение и удаление загруженного.
7. Повторная загрузка в тот же файл идемпотентна.
8. Изменение метаинформации не затрагивает шифротекст и выполняется отдельной
   операцией.
9. Проверка содержимого антивирусом невозможна: сервер видит только шифротекст.
   Это следствие модели и должно быть объявлено пользователю.

### 4.7 Скачивание файла

1. Клиент запрашивает файл, получает метаданные и обёрнутый ключ содержимого.
2. Клиент разворачивает ключ содержимого закрытым ключом.
3. Клиент получает шифротекст потоком и расшифровывает его.
4. Поддерживается докачка по диапазону: шифрование потоковое, произвольный
   отрезок расшифровывается без чтения файла целиком.
5. Отказ аутентификации AEAD — содержимое повреждено или подменено; данные не
   отдаются пользователю.

### 4.8 Директории

1. Создание: клиент шифрует имя ключом учётной записи, указывает родителя.
2. Переименование и перемещение меняют только метаданные.
3. Удаление непустой директории требует явного признака рекурсии.
4. Циклы запрещены: директория не может стать потомком самой себя.
5. Права наследуются от директории к содержимому; право, заданное у файла,
   сильнее унаследованного.

### 4.9 Теги и поиск

1. Тег — произвольная строка, задаваемая владельцем. Значение нормализуется на
   клиенте (регистр, пробелы, форма Unicode) до вычисления метки, иначе
   «Отчёты», «отчёты» и «Отчёты » окажутся разными тегами.
2. Клиент шифрует значение тега ключом учётной записи и вычисляет
   детерминированную метку `HMAC(ключ тегов, нормализованное значение)`.
3. Сервер хранит зашифрованное значение и метку. Метка позволяет ему
   группировать и фильтровать файлы по равенству тега, не зная самого тега.
4. **Известное ограничение:** детерминированная метка допускает частотный
   анализ. Наблюдатель с доступом к базе видит, что N файлов имеют один и тот же
   тег, и может сопоставить распределение с известным. Значения тегов при этом
   остаются скрытыми. Ограничение принято осознанно ради серверной фильтрации;
   пользователь предупреждается, что теги менее защищены, чем имена файлов.
5. Поиск по тегу выполняется сервером по метке. Поиск по имени и по
   метаинформации выполняется клиентом после расшифровки: сервер их не видит.
6. Ключ тегов выводится из ключа учётной записи, поэтому смена пароля метки не
   меняет и переиндексации не требует.
7. Теги относятся к закрытой метаинформации и при выдаче доступа не передаются.

### 4.10 Выдача доступа

1. Клиент разворачивает ключ содержимого своим закрытым ключом.
2. Клиент получает открытый ключ получателя и **сверяет его отпечаток**: без
   сверки сервер может подставить свой ключ и получить доступ.
3. Клиент оборачивает открытым ключом получателя **ключ метаданных** — всегда, —
   и **ключ содержимого** — только если выдаётся право читать содержимое.
   Получатель без права чтения видит имя и публичную метаинформацию, но не
   содержимое.
4. Закрытая метаинформация и теги не передаются: они зашифрованы ключом учётной
   записи владельца, которого у получателя нет.
5. Клиент отправляет обёрнутые ключи вместе с правами и сроком действия.
6. Права выдаваемой ссылки — подмножество прав выдающего.
7. Для закрытой и публичной ссылки генерируется отдельная пара ключей; секретная
   часть помещается **во фрагмент адреса** (`https://host/s/<id>#<ключ>`).
   Фрагмент не отправляется на сервер. Ограничение: такой адрес попадает в
   историю браузера и в буфер обмена, о чём пользователь предупреждается.

### 4.11 Отзыв доступа

1. Отзыв ссылки запрещает **новые** обращения.
2. Отзыв **не отменяет знания ключа** тем, кто его уже получил, и не делает
   ранее скачанное недоступным. Формулировка в интерфейсе должна быть именно
   такой.
3. Полный отзыв требует ротации: клиент генерирует новый ключ содержимого,
   перешифровывает файл и заново выдаёт доступ оставшимся. Операция
   пропорциональна размеру файла и выполняется по явному запросу.

### 4.12 Удаление

1. Удаление файла уничтожает все ключи доступа к его содержимому. Содержимое без
   ключа невосстановимо даже при сохранившихся блоках.
2. Удалённое помещается в корзину на объявленный срок, затем стирается
   окончательно вместе с шифротекстом.
3. Квота освобождается в момент окончательного удаления.

### 4.13 Сессии

1. Срок жизни сессии задаётся конфигурацией.
2. Сессия продлевается при обращении, но не дольше предельного срока с момента
   создания.
3. Пользователь видит список активных сессий и может завершить любую или все.
4. Смена пароля завершает все сессии, кроме текущей.
5. Токен передаётся заголовком `Authorization: Bearer`. Если используется кука,
   она обязана нести `HttpOnly`, `Secure`, `SameSite=Strict`.
6. Сервер хранит хеш токена, а не токен.

### 4.14 Экспорт и удаление учётной записи

1. Пользователь может выгрузить все свои данные: метаданные и шифротексты.
   Расшифровка выполняется его клиентом.
2. Удаление учётной записи стирает ключи, содержимое, журнал сверх срока
   хранения и внешние привязки.
3. Срок отложенного удаления объявляется заранее.

## 5. Квоты

- Квота считается по **размеру шифротекста**, а не открытого текста.
- Расходуется квота **владельца содержимого**. Выдача доступа чужую квоту не
  расходует: иначе один пользователь исчерпывает квоту другого без его согласия.
- Проверка квоты не имеет побочных эффектов; изменение счётчика выполняется при
  создании, окончательном удалении и ротации ключа.
- Счётчики — 64-разрядные.
- Превышение предела на один файл и исчерпание квоты различаются кодом ответа.

## 6. Ограничения загрузки

- Максимальный размер файла и суммарный размер запроса — из конфигурации.
- Обрыв передачи не оставляет частичных данных, занимающих квоту.
- Докачка поддерживается.
- Проверка типа содержимого невозможна; ограничения по расширению бессмысленны и
  не вводятся. Ориентир по остальным рискам:
  <https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html>

## 7. Аудит операций

Журнал служит двум разным целям, и их нельзя смешивать: пользователю он нужен,
чтобы заметить чужой доступ к своим файлам, а эксплуатации — чтобы расследовать
инциденты.

Записываются:

| Категория | События |
| --- | --- |
| Доступ | Вход, выход, неудачные попытки входа, создание и завершение сессий |
| Учётная запись | Смена пароля, использование ключа восстановления, подтверждение почты и телефона, привязка и отвязка внешних личностей, изменение второго фактора |
| Данные | Создание, изменение метаинформации, перемещение, удаление и восстановление файлов и директорий, ротация ключа содержимого |
| Доступ к данным | Скачивание содержимого, выдача и отзыв доступа, обращение по ссылке — с указанием, кто обратился |
| Администрирование | Изменение квот, блокировка учётной записи |

Требования:

- Каждая запись содержит: время, пользователя, сессию, действие, объект,
  результат, адрес и сведения о клиенте.
- **В журнал не попадают:** пароли, аутентификационные хеши, токены, любые
  ключи, открытые имена файлов, значения тегов, содержимое. Объекты
  указываются идентификаторами; имя пользователь видит, расшифровав его сам.
- Владелец видит обращения к своим файлам, включая обращения получателей
  ссылок: это единственный способ заметить утечку выданного доступа.
- Журнал доступен только на чтение. Пользователь не может удалить или изменить
  свои записи — иначе он бесполезен как средство расследования.
- События, требующие внимания (вход с нового устройства, использование ключа
  восстановления, массовое скачивание), сопровождаются уведомлением на
  подтверждённую почту.
- Срок хранения объявляется и соблюдается; по его истечении записи стираются.
  Удаление учётной записи стирает журнал сверх срока, необходимого по закону.

## 8. Защита от подбора и злоупотреблений

- Ограничение частоты на вход, регистрацию, восстановление, подтверждение кодов
  и обратные вызовы внешних провайдеров.
- Прогрессивная задержка и временная блокировка после серии неудач.
- Одноразовые коды подтверждения: ограниченный срок, ограниченное число попыток,
  хранение хешем.
- Второй фактор: TOTP либо WebAuthn. Требования к аутентификации — NIST SP
  800-63B: <https://pages.nist.gov/800-63-3/sp800-63b.html>

## 9. Персональные данные

- Собираются: адрес почты, опционально телефон и отображаемое имя, адреса и
  сведения о клиентах в журнале.
- Обращения к внешним сервисам за аватарами и любыми иными данными запрещены.
- Экспорт и удаление данных — по разделу 4.14.

## 10. Требования к API

- Внешний HTTP API строится по парадигме RESTful; правила — в
  [CLAUDE.md](CLAUDE.md). Ориентир по безопасности:
  <https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html>
- API документируется спецификацией OpenAPI 3.1, генерируемой из кода.
- Ошибки — `application/problem+json` по RFC 9457:
  <https://www.rfc-editor.org/rfc/rfc9457>
- API версионируется заголовком — см. раздел 10.1.
- Ответы не раскрывают существования чужих ресурсов: для субъекта без доступа
  ресурс неотличим от несуществующего.
- Семантика методов и кодов — по RFC 9110:
  <https://www.rfc-editor.org/rfc/rfc9110>

### 10.1 Версионирование

**Решение: версия передаётся заголовком запроса `API-Version`, в пути её нет.**
Путь ресурса — `/api/files/{id}`, а не `/api/v1/files/{id}`.

Обоснование выбора:

- URI обязан идентифицировать ресурс, а не его представление. Версия контракта —
  свойство представления, поэтому её место в заголовке. При версии в пути
  `/api/v1/files/42` и `/api/v2/files/42` формально оказываются разными
  ресурсами, хотя это один и тот же файл; ссылки, `Location` и `ETag` начинают
  зависеть от версии клиента.
- Согласование через `Accept: application/vnd.cstorage.v1+json` формально
  правильнее выделенного заголовка, но неприменимо целиком: `GET
  /api/files/{id}/content` отдаёт `application/octet-stream`, и версию туда без
  изобретения нестандартного типа не вставить. Заголовок работает единообразно
  для JSON и для двоичного содержимого.
- Префикс `X-` не используется: RFC 6648 объявляет его устаревшим
  (<https://www.rfc-editor.org/rfc/rfc6648>). Отсюда имя `API-Version`, а не
  `X-API-Version`.

Правила:

1. **Значение** — целое число текущей версии контракта: `API-Version: 1`.
2. **Умолчание.** При отсутствии заголовка применяется **самая старая
   поддерживаемая** версия, а не самая новая. Клиент, написанный под первую
   версию и не присылающий заголовок, не сломается в день выпуска второй.
   Тот же подход у GitHub:
   <https://docs.github.com/en/rest/about-the-rest-api/api-versions>
3. **Неизвестная версия** — `400` с телом `application/problem+json`, где
   перечислены поддерживаемые версии. Код `406` не используется: он относится к
   согласованию содержимого через `Accept`, а здесь механизм иной.
4. **`Vary: API-Version`** обязателен на каждом версионируемом ответе, иначе
   промежуточный кэш отдаст представление чужой версии (RFC 9111:
   <https://www.rfc-editor.org/rfc/rfc9111>).
5. **Эхо в ответе.** Каждый ответ несёт `API-Version` с фактически применённой
   версией — клиент видит, что его заголовок понят.
6. **Вне версионирования** остаются служебные маршруты: спецификация
   `/api/openapi.json`, документация `/api/docs`, пробы готовности и живости.
   Они не являются частью контракта данных.
7. **Устаревание** объявляется заголовками `Deprecation` и `Sunset` по RFC 8594
   (<https://www.rfc-editor.org/rfc/rfc8594>) на ответах уходящей версии, с
   объявленным сроком снятия. После снятия версия отвечает `410`.
8. **Наблюдаемость.** Применённая версия кладётся в поля `tracing` и в метрики
   явно: в отличие от версии в пути, из строки запроса она не видна.
9. **В спецификации** `API-Version` описывается как параметр-заголовок каждой
   версионируемой операции; на каждую версию публикуется отдельный документ
   OpenAPI.
10. **Сосуществование версий** в коде выражается отдельными модулями
    представлений и отдельными деревьями маршрутов, выбираемыми на входе по
    значению заголовка. Ветвление по версии внутри обработчиков запрещено: оно
    расползается по коду и нарушает единственную ответственность.

## 11. Коды ответов

Список сокращён до применяемых. Каждый код возвращается в перечисленных
случаях и не используется произвольно.

| Код | Значение | Где применяется |
| --- | --- | --- |
| `200` | OK | Успешное чтение |
| `201` | Created | Создание пользователя, сессии, файла, директории, ссылки; обязателен `Location` |
| `204` | No Content | Успех без тела: удаление, загрузка содержимого, завершение сессии |
| `206` | Partial Content | Скачивание по диапазону |
| `304` | Not Modified | Условный запрос с `If-None-Match` |
| `400` | Bad Request | Некорректный синтаксис запроса; неизвестное значение `API-Version` |
| `401` | Unauthorized | Токен отсутствует, недействителен или истёк |
| `403` | Forbidden | Токен действителен, но действие не разрешено |
| `404` | Not Found | Ресурс отсутствует либо недоступен субъекту |
| `405` | Method Not Allowed | Метод не поддерживается ресурсом |
| `409` | Conflict | Логин занят; конфликт версий ресурса |
| `410` | Gone | Ссылка отозвана или истекла; запрошена снятая с поддержки версия API |
| `412` | Precondition Failed | Несовпадение `If-Match` |
| `413` | Content Too Large | Превышен предел размера файла |
| `415` | Unsupported Media Type | Неподдерживаемый тип тела запроса |
| `416` | Range Not Satisfiable | Некорректный диапазон при скачивании |
| `422` | Unprocessable Content | Синтаксис верен, значения недопустимы |
| `428` | Precondition Required | Изменение без `If-Match` там, где он обязателен |
| `429` | Too Many Requests | Превышено ограничение частоты |
| `500` | Internal Server Error | Непредвиденный отказ; всегда попадает в журнал |
| `503` | Service Unavailable | Временная недоступность, с `Retry-After` |
| `507` | Insufficient Storage | Исчерпана дисковая квота |

Исключены как неприменимые: `402` (сервис не платный), `424` и `425` (WebDAV и
изъятая из стандарта семантика), `426`, `449` (проприетарное расширение, в
стандарт не входит), а также информационные `100` и `102`.

## 12. Открытые вопросы

1. **Подмена клиента активным администратором** — принципиально не решается для
   веб-клиента, доставляемого сервером. Смягчения: подписанные сборки, нативные
   и мобильные клиенты, воспроизводимая сборка, публикация отпечатков. Требует
   решения до заявлений о свойствах безопасности в публичных материалах.
2. **Сверка отпечатков открытых ключей** между пользователями — нужен ли
   интерфейс сверки и как он выглядит.
3. **Сокрытие размеров файлов** паддингом — принято решение не скрывать;
   пересмотреть, если появится соответствующее требование.
4. **Публичные ссылки и предпросмотр** — предпросмотр требует расшифровки на
   клиенте получателя; объём работы оценить отдельно.
5. **Совместное редактирование и версии файлов** — за пределами первой версии.
