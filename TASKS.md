## TASK-011 — Ресурс `/api/users`

**Приоритет:** P1  **Статус:** ОПИСАН

### Контекст

Прежний `POST /rest/register` принимал учётные данные в заголовке
`Authorization: BASIC`, разбирая его дублирующимся и дырявым кодом
(`web/.../rest/RegisterController.kt:16-23`,
`web/.../rest/AuthenticateController.kt:26-33`): проверка `contains("BASIC")`
вместо `startsWith`, жёсткий `substring(5)`, обращение к `content[1]` без
проверки, `split(":")` без ограничения — пароль с двоеточием ломался. Ответ
`Response.created(null)` не содержал `Location`.

### Что делать

0. Маршруты, представления и общие правила зафиксированы в `TODO.md`,
   раздел 10.3; дублировать их здесь не нужно, расхождение — ошибка.
1. `POST /api/users` — регистрация. Учётные данные передаются в теле JSON, а
   не в заголовке Basic: регистрация не является аутентификацией.
2. Ответ `201` с заголовком `Location` на созданный ресурс и представлением без
   единого ключа.
3. Повторное имя — `409`.
4. Нарушение требований к паролю — `422` с указанием, какое требование не
   выполнено.
5. `GET /api/users/me` — профиль текущего субъекта.
6. Разбор `Authorization` для входа (TASK-012) — один значимый тип,
   используемый в единственном месте.

### Как проверить

Тест: регистрация возвращает `201` с корректным `Location`. Тест: повторная
регистрация имени возвращает `409`. Тест: пароль с двоеточием работает.

## TASK-043 — Реализовать вход через VK и Telegram

**Приоритет:** P1  **Статус:** ОПИСАН

### Контекст

Требования и порядок обмена с провайдерами зафиксированы в `TODO.md`,
раздел 4.3: маршруты, обязательные проверки, поведение сессии без развёрнутых
ключей. Задача — реализация. Она следует за TASK-012, потому что переиспользует
ресурс сессий, и за TASK-007, потому что опирается на признак «ключи
развёрнуты».

Ключевое следствие модели, которое нельзя нарушить: **учётная запись через
внешний вход не создаётся**. Без пароля не из чего вывести мастер-ключ, поэтому
внешний вход открывает доступ только к уже существующей записи с привязанной
внешней личностью, и созданная им сессия к содержимому доступа не даёт.

### Выбор библиотек

Проверено на момент постановки задачи:

| Крейт | Версия | Назначение |
| --- | --- | --- |
| `oauth2` | 5.0.0 | Authorization code + PKCE, обмен кода на токен. <https://docs.rs/oauth2/latest/oauth2/> |
| `openidconnect` | 4.0.1 | Надстройка для OIDC: discovery, проверка `id_token` и `nonce`. <https://docs.rs/openidconnect/latest/openidconnect/> |

Решение: `oauth2` для VK. `openidconnect` подключать только если VK ID
действительно выдаёт `id_token` — проверить при реализации; иначе это лишняя
зависимость. Для Telegram библиотека не нужна: проверка подписи пишется на
`hmac` и `sha2` и покрывается тестами с эталонными векторами.

Обе библиотеки позволяют отключить встроенный HTTP-клиент и передать свой, что
соответствует требованию `RULE.md` о `default-features = false` и избавляет от
второго транспорта в графе зависимостей.

### Что делать

1. Ввести трейт внешнего провайдера с одной зоной ответственности: по артефактам
   провайдера вернуть проверенную внешнюю личность либо отказать. Две
   реализации — VK и Telegram; общего OAuth2-слоя у них нет.
2. Реализовать `POST /api/sessions/authorizations`, служебный
   `GET /auth/{provider}/callback` и приём артефактов в `POST /api/sessions`.
3. Запрос авторизации — одноразовый, с коротким сроком жизни, привязанный к
   начавшему процедуру клиенту; `state` и `code_verifier` хранятся вместе с ним
   и не покидают сервер.
4. Проверки VK: PKCE `S256`, совпадение `state`, посимвольное сравнение
   `redirect_uri`, обмен кода только на сервере.
5. Проверки Telegram: `HMAC-SHA256` с ключом `SHA256(токен бота)`, сравнение в
   постоянном времени, окно свежести `auth_date`, защита от повтора по паре
   «идентификатор + `auth_date`».
6. Привязка внешней личности — отдельная операция из уже аутентифицированной
   сессии; автоматическое связывание по почте не реализуется ни при каких
   условиях.
7. Отвязка запрещена, если она оставит учётную запись без способов входа.
8. Секреты провайдеров — только из конфигурации (TASK-009), без значений по
   умолчанию; в журнал не попадают (TASK-017).
9. Ограничение частоты на обратных вызовах — общее с TASK-036.

### Как проверить

Тест: сессия, созданная внешним входом, отвечает `403` на запрос содержимого
файла и `200` на запрос профиля. Тест: повторное предъявление тех же данных
Telegram отвергается. Тест: ответ провайдера с чужим `state` отвергается. Тест:
внешний вход для непривязанной личности не создаёт учётную запись.

## TASK-040 — Метаинформация о файле трёх категорий

**Приоритет:** P1  **Статус:** ОПИСАН

### Контекст

Требуется метаинформация файла с разграничением видимости: **закрытая** — только
владельцу, **техническая** — для нужд системы, **публичная** — видна снаружи при
передаче прав. Модель зафиксирована в `TODO.md`, раздел 3, сущность
«Метаинформация файла».

В модели C разграничение видимости обеспечивается не проверкой прав на сервере,
а **разными ключами шифрования**: сервер физически не способен показать то, чего
не может расшифровать. Это надёжнее любой проверки в коде.

| Категория | Кому видна | Чем защищена |
| --- | --- | --- |
| Техническая | Серверу и всем, у кого есть доступ | Не шифруется |
| Публичная | Владельцу и получателям прав | Ключ метаданных файла |
| Закрытая | Только владельцу | Ключ учётной записи |

Постановка задачи вскрыла дефект первоначальной спецификации: имя файла
шифровалось ключом учётной записи, а значит получатель ссылки не увидел бы даже
названия файла, к которому получил доступ. Исправлено введением **отдельного
ключа метаданных файла**, обёртываемого вместе с ключом содержимого.

### Что делать

1. Ввести ключ метаданных файла (TASK-003, TASK-033): генерируется при создании
   файла, оборачивается открытым ключом владельца и каждого получателя.
2. Разделить хранение на три поля: техническая метаинформация открытым текстом,
   публичная и закрытая — двумя разными шифротекстами.
3. Техническая категория заполняется **сервером**; значения, присланные
   клиентом, для неё игнорируются. Иначе клиент сможет соврать о размере и хеше.
4. Публичная категория допускает произвольные пары «ключ-значение» от владельца
   сверх обязательных полей (имя, расширение, тип содержимого, описание, размер
   открытого текста). Предельный размер — из конфигурации.
5. Изменение метаинформации — отдельная операция, не затрагивающая шифротекст.
6. Перевод сведения из закрытой категории в публичную — явная операция с
   перешифрованием, а не смена флага. Обратный перевод не возвращает
   конфиденциальности: получатели уже видели значение, и интерфейс обязан об
   этом предупреждать.
7. Право видеть публичную метаинформацию отделено от права читать содержимое:
   получателю, которому выдано только первое, ключ содержимого не передаётся
   вовсе (`TODO.md` 4.10, шаг 3).
8. Условные запросы `ETag`/`If-Match` — на метаинформацию, чтобы одновременное
   редактирование с двух устройств не затирало чужие изменения.

### Как проверить

Тест: получатель доступа читает публичную метаинформацию и не может расшифровать
закрытую. Тест: получатель без права чтения содержимого видит имя, но получает
`403` на содержимое. Тест: техническая метаинформация, присланная клиентом,
игнорируется — сервер записывает собственные значения. Тест: изменение
метаинформации не меняет шифротекст и его хеш.

## TASK-035 — Логические директории

**Приоритет:** P1  **Статус:** ОПИСАН

### Контекст

`TODO.md` описывает сущность «Директория» и сценарий 4.8. В прежней реализации
директорий не было вовсе — файлы лежали плоским списком, хотя в спецификации они
присутствовали с самого начала.

Особенность модели C: имя директории зашифровано ключом учётной записи, поэтому
сервер не может ни сортировать по имени, ни искать по нему. Дерево строится по
идентификаторам родителей, которые серверу видны.

### Что делать

0. Маршруты, представления и общие правила зафиксированы в `TODO.md`,
   раздел 10.3; дублировать их здесь не нужно, расхождение — ошибка.
1. Реализовать ресурс директорий по контракту TASK-002: создание, чтение
   содержимого, переименование, перемещение, удаление.
2. Переименование и перемещение меняют только метаданные, содержимое файлов не
   трогается.
3. Удаление непустой директории требует явного признака рекурсии; без него —
   отказ с `409`.
4. Циклы запрещены: директория не может стать потомком самой себя. Проверка на
   стороне сервера, поскольку дерево ему видно.
5. Права наследуются от директории к содержимому; право, заданное у файла,
   сильнее унаследованного (`TODO.md` 4.8, шаг 5).
6. Глубина вложенности ограничена конфигурацией: неограниченная глубина
   превращает рекурсивные операции в способ исчерпать ресурсы.
7. Сортировка и поиск по имени выполняются клиентом после расшифровки — записать
   это как известное ограничение, чтобы никто не «оптимизировал» его хранением
   открытого имени.

### Как проверить

Тест: попытка сделать директорию потомком самой себя отклоняется. Тест: удаление
непустой директории без признака рекурсии отвечает `409`. Тест: открытые имена
директорий отсутствуют в базе и в ответах API.

## TASK-020 — Property-тесты криптографических преобразований

**Приоритет:** P2  **Статус:** ОПИСАН

### Контекст

`RULE.md` требует `proptest` для любой функции с нетривиальным пространством
входных данных — парсеров, валидаторов, round-trip. Крипто-слой и значимые типы
подпадают под это определение полностью. Прежняя реализация не имела ни одного
теста на криптографию: дефекты вроде усечения пароля до 16 символов не были бы
пойманы никаким числом примеров, написанных вручную.

### Что делать

1. Round-trip: шифрование и расшифровка содержимого произвольной длины, включая
   нулевую, возвращают исходные байты.
2. Round-trip обёртывания симметричного ключа парой ключей.
3. Выведение ключа: разные пароли дают разные ключи; один пароль с разными
   солями даёт разные ключи; пароль произвольной длины и произвольного
   Unicode-содержимого не приводит к отказу.
4. Значимые типы: `ContentHash`, `Username`, `Quota` принимают ровно допустимое
   множество и отвергают всё остальное.
5. Устойчивость к порче: изменение любого байта шифротекста или тега приводит к
   отказу расшифровки.
6. Сериализация представлений: round-trip через JSON не теряет и не добавляет

## TASK-041 — Тегирование файлов

**Приоритет:** P2  **Статус:** ОПИСАН

### Контекст

Требуются теги для поиска и группировки файлов. Модель — `TODO.md`, раздел 3
(сущности «Тег», «Тег файла») и сценарий 4.9.

Основная сложность в модели C: зашифрованное значение тега сервер сопоставить не
может — два шифрования одной строки дают разные шифротексты, и группировка
становится невозможной. Решение — **детерминированная метка**
`HMAC(ключ тегов, нормализованное значение)`: сервер сравнивает и группирует по
меткам, не зная значений.

Ключ тегов выводится из ключа учётной записи, поэтому смена пароля метки не
меняет и переиндексации не требует.

### Что делать

0. Маршруты, представления и общие правила зафиксированы в `TODO.md`,
   раздел 10.3; дублировать их здесь не нужно, расхождение — ошибка.
1. Нормализация значения на клиенте до вычисления метки: регистр, обрезка
   пробелов, форма Unicode NFC. Без неё «Отчёты», «отчёты» и «Отчёты » станут
   разными тегами.
2. Клиент отправляет пару: зашифрованное значение и метка. Сервер значение не
   интерпретирует.
3. Фильтрация и группировка по меткам — на сервере; поиск по имени и
   метаинформации — на клиенте после расшифровки. Записать это ограничение явно,
   чтобы никто не «оптимизировал» его хранением открытых значений.
4. Теги относятся к **закрытой** метаинформации (TASK-040) и при выдаче доступа
   не передаются.
5. Ограничения: предельная длина значения, предельное число тегов на файл,
   предельное число тегов на пользователя — из конфигурации.
6. Переименование тега перешифровывает значение и пересчитывает метку у всех
   файлов владельца — операция пропорциональна числу файлов, выполняется по
   явному запросу.

### Известное ограничение

Детерминированная метка допускает **частотный анализ**: наблюдатель с доступом к
базе видит, что N файлов помечены одинаково, и может сопоставить распределение с
известным ему. Значения тегов при этом остаются скрытыми. Ограничение принято
осознанно ради серверной фильтрации и зафиксировано в `TODO.md` 4.9; интерфейс
предупреждает, что теги защищены слабее имён файлов.

Альтернатива без этого недостатка — полностью клиентский поиск с выгрузкой всех
тегов. Оценить её стоимость на реальном числе файлов до реализации: если
выгрузка приемлема, детерминированные метки не нужны вовсе.

### Как проверить

Тест: файлы с одинаковым тегом группируются сервером. Тест: значения тегов
отсутствуют в базе в открытом виде. Тест: получатель выданного доступа тегов
владельца не видит. Тест: «Отчёты» и «отчёты » дают одну метку.

### Контекст

`web/` и `pom.xml` остаются справочным материалом на время перехода. Держать их
дольше необходимого вредно: два источника истины расходятся, а сборка Maven на
текущем окружении всё равно не работает.

### Что делать

1. Определить критерий паритета: все сценарии из `TODO.md`, покрытые
   интеграционными тестами (TASK-019), проходят на Rust-реализации.
2. Сверить, что ни один документ не ссылается на удаляемые файлы: `CLAUDE.md`,
   `README` (TASK-027), `TODO.md`.
3. Удалить `web/` и `pom.xml` одним коммитом с внятным сообщением: история
   остаётся в git, восстановить можно всегда.
4. Убрать из `.gitignore` записи, относящиеся к Maven и IDE Java, добавить
   `target/` для Cargo.

### Как проверить

После удаления пять ворот и интеграционные тесты проходят; в репозитории не
остаётся ссылок на удалённые пути.
