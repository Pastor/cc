## Проект

`cstorage` (репозиторий `cc`) — сервер криптографического файлового хранилища.
Файл шифруется симметричным ключом, симметричный ключ шифруется открытым ключом
владельца и хранится рядом. Закрытый ключ пользователя хранится зашифрованным
его паролем и расшифровывается только на время сессии, в памяти.

### Состояние

Проект переводится на **Rust**. Прежняя реализация на Kotlin (`web/`, `pom.xml`)
остаётся в репозитории как справочный материал: она содержит рабочую модель
предметной области и одновременно набор известных дефектов, которые в новой
реализации повторять нельзя. Каждый такой дефект зафиксирован как требование в
соответствующей задаче `TASKS.md`.

Kotlin-код удаляется только после достижения функционального паритета.

### Целевой стек

Задаётся [RULE.md](RULE.md):

| Слой | Технология |

| Язык | Rust stable, MSRV в `rust-toolchain.toml`, edition 2021/2024 |
| Runtime | `tokio`, единственный в процессе |

### Модель безопасности

Гибридная схема: ключи выводятся и применяются **на клиенте**, сервер хранит
только шифротекст и обёрнутые ключи. Полное описание, ключевая иерархия и модель
угроз — в `TODO.md`, раздел 1. Кратко:

- Пароль на сервер не передаётся никогда. Из него на клиенте выводится
  мастер-ключ, из него двумя ветвями — ключ шифрования (остаётся у клиента) и
  аутентификационный хеш (уходит на сервер вместо пароля).
- Сервер не располагает материалом для расшифровки содержимого — ни в покое, ни
  во время работы. Метода, отдающего ключ, в API нет, потому что ключа нет у
  сервера.
- Содержимое, имена файлов и директорий шифруются на клиенте. Серверу видны
  размеры, время операций и граф доступа — это принято осознанно.
- Работа с сервисом — только по TLS 1.3; авторизованные вызовы несут сессионный
  токен.
- Забытый пароль без ключа восстановления означает безвозвратную потерю доступа
  к файлам.

Два ограничения принципиальны и устранению в этой архитектуре не подлежат:
подменённый сервером веб-клиент способен похитить пароль, а отзыв доступа не
отменяет знания ключа тем, кто его уже получил. Обещать обратное запрещено.

Алгоритмы зафиксированы в `TODO.md`, раздел 2, и реализацией не выбираются.


Ниже — правила, которых в `RULE.md` нет. Они дополняют его, а не спорят с ним.

### Внешний HTTP API — RESTful

Любой внешний HTTP API проектируется по парадигме RESTful. Требования:

- **Ресурсы — существительные во множественном числе**, без глаголов в пути:
  `/streams`, а не `/stream/list`; `/sessions`, а не `/authenticate`.
- **Действие выражает HTTP-метод**, а не путь. `POST /sessions` вместо
  `POST /login`; `DELETE /sessions/current` вместо `POST /me/logout`.
- **Иерархия ресурсов явная**: коллекция `/streams`, элемент `/streams/{id}`,
  подчинённый ресурс `/streams/{id}/content`, `/streams/{id}/links`.
- **Семантика методов соблюдается**: `GET` безопасен и не имеет побочных
  эффектов; `PUT` и `DELETE` идемпотентны; `POST` — нет. Метод, меняющий
  состояние в ответ на `GET`, — ошибка проектирования.
- **Коды ответов осмысленны**. Создание — `201 Created` с заголовком `Location`.
  Успех без тела — `204 No Content`. Список допустимых кодов — в `TODO.md`,
  раздел «Используемые коды».
- **API версионируется заголовком `API-Version`, не путём.** Путь — это
  `/api/files/{id}`, а не `/api/v1/files/{id}`: URI идентифицирует ресурс, а
  версия относится к представлению. Отсутствие заголовка означает самую старую
  поддерживаемую версию, неизвестная версия — `400`. Каждый версионируемый
  ответ несёт `Vary: API-Version` и эхо применённой версии. Ломающее изменение
  выпускается новой версией; устаревание объявляется заголовками `Deprecation`
  и `Sunset`. Полные правила — `TODO.md`, раздел 10.1.
- **Тело — JSON**. Ошибки — `application/problem+json` по RFC 9457, единым
  форматом для всего API.
- **Коллекции пагинируются** и возвращают стабильный порядок.
- **Условные запросы** через `ETag` и `If-Match` там, где ресурс изменяем.
- **Сервер не хранит состояния сессии** сверх того, что необходимо для токена.
- **Ничего лишнего в представлении**: наружу отдаётся отдельный тип
  представления, а не доменная сущность. Вывод `Serialize` на внутренней
  структуре запрещён — `RULE.md` прямо называет это способом молча утечь данные
  при добавлении поля.

### Документирование API — OpenAPI

- Каждый внешний HTTP API описан спецификацией OpenAPI 3.1.
- Спецификация **генерируется из кода** (`utoipa` или `aide`), а не пишется
  отдельным файлом руками: рукописная спецификация неизбежно расходится с
  реализацией.
- Спецификация публикуется по `/api/openapi.json`, интерактивная документация —
  по `/api/docs`; на каждую версию контракта — отдельный документ. Служебные
  маршруты в версионировании не участвуют.
- Маршрут и его описание регистрируются **одним объявлением** (`utoipa-axum`):
  расхождение между ними должно быть невозможно по построению, а не
  отлавливаться тестом задним числом.
- Для каждой операции документированы: краткое описание, все коды ответов, схемы
  запроса и ответа, примеры, требования аутентификации.
- Тест проверяет, что спецификация валидна и что в ней нет маршрута без
  описания, а в приложении — маршрута без записи в спецификации.
- **Изменение API без обновления спецификации не принимается.** Это шестые
  ворота в дополнение к пяти из `RULE.md`.

### Инструменты

Использовать GNU-инструменты: `gsed`, `gfind`, `ggrep`, `gcat`. Коммитить через
`git commit` с осмысленным сообщением. Pull request — через `git push` +
`gh pr create`. Issue — через `gh issue create`.

### Дисциплина

Отвечать в чате коротко. Писать лаконичную, прямую, человеческую прозу.
Возражать при технических ошибках, но уступать пользователю в вопросах видения
и архитектуры. Держаться в рамках задачи, рефакторить только то, что требуется.
Проектировать сверху вниз: сначала целое, потом части; сначала композиция,
потом ингредиенты.

### Рабочий процесс

Перед изменениями делать pull из Git; push — только с явного разрешения
пользователя. Ветку называть по номеру GitHub-issue, спрашивать при
неуверенности. Всегда практиковать TDD: воспроизводить баг тестом до
исправления. Вкладываться в тесты, пока баг не воспроизведётся, доверяя
интуиции больше, чем отладке. Логировать обильно через `tracing`, когда
проблема остаётся сложной.

### Изменения

Терпеть баги в upstream — предлагать issue и ждать исправления. Держать
изменения сфокусированными и минимальными. Оставлять загадки на потом, следуя
Puzzle Driven Development. Отмечать «запахи» и рефакторинг — заводить задачу, а
не исправлять молча. Исправлять нарушения стиля, доверяя проверяльщикам
(`clippy`, `rustfmt`), а не подавляя их огульными `#[allow]`.

### Проза и именование

Предпочитать эстетику функциональности. Пропускать инлайн-комментарии — их
место занимает `///` на `pub`-элементах, как требует `RULE.md`. Называть
переменные одиночными существительными. Инлайнить одноразовые выражения, убирая
ненужные локальные переменные. Называть функции одиночными существительными или
глаголами, разделяя команды и запросы. Паковать тела функций без пустых строк.

Отвергать имена на «-ер» и модули-свалки: `Manager`, `Helper`, `Utils`,
`Service`, `Handler` в имени типа — признак того, что ответственность не
названа. Тип называется по тому, чем он является.

**Идентификаторы — только латиницей.** Кириллица в именах функций, методов,
переменных, полей, типов, модулей и крейтов запрещена, включая имена тестов.
Русский остаётся языком сообщений об ошибках, логов, документации и
комментариев — но не языком кода.

### Стиль

Сообщения об ошибках и логи — одно предложение с контекстом. Убирать точки в
конце сообщений. Держать один язык сообщений во всём проекте. Следовать «Парным
скобкам» и «Монотонному отступу».

**Парные скобки** (Paired Brackets): открывающая и закрывающая скобки всегда на
одном уровне отступа; тело между ними сдвинуто ровно на один уровень вправо.
Касается фигурных, круглых и квадратных скобок.

**Монотонный отступ** (Monotonic Indentation): отступ внутри блока только растёт
или остаётся на месте — никогда не прыгает назад-вперёд. Каждая вложенность
добавляет ровно один уровень. Если отступ «скачет», код надо переструктурировать:
вынести логику в отдельную функцию или упростить вложенность. Глубина вложенности
свыше трёх уровней — сигнал к `let ... else` и раннему возврату.

### Объекты

Чтить SOLID (единственная ответственность, открытость/закрытость, подстановка
Лисков, разделение интерфейсов, инверсия зависимостей). Следовать DDD и YAGNI.
Применять SRP и DRY. Предпочитать немедленный отказ молчаливому.

В приложении к Rust:

- Тип имеет от одного до четырёх полей. Пять полей — это два типа, притворяющихся
  одним.
- Тип неизменяем по умолчанию: методы принимают `&self`, `&mut self` — осознанное
  исключение. Изменение возвращает новое значение.
- Инвариант проверяется в конструкторе. Тип, который можно собрать в
  недопустимом состоянии, спроектирован неверно.
- Значимые типы вместо голых примитивов: `StreamId`, `ContentHash`, `Quota` —
  не `String` и не `u64`. Это то же требование, что «отвергай проверку типов и
  приведение».
- Композиция вместо наследования поведения: `RULE.md` требует маленьких
  сфокусированных трейтов, и это тот же принцип.
- Никакого глобального изменяемого состояния: ни `static mut`, ни
  `lazy_static!` с изменяемой коллекцией. Состояние передаётся явно.
- Отсутствие — это `Option`, отказ — это `Result`. `Option` не используется,
  чтобы скрыть ошибку.

### Тесты

Следовать «Злым тестам». Одно утверждение на тест — последним оператором.
Формулировать сообщения об ошибках негативно. Держать тесты короткими: одно
поведение, одно утверждение. Сопоставлять тестовые файлы один-к-одному с
модулями, называя тесты как предложения. Изолировать тесты от общего состояния,
разделяемых фикстур и порядка выполнения.

**Злые тесты (Angry Tests)**: каждый тест проверяет ровно одно поведение с одним
утверждением; сообщение об ошибке описывает, что пошло не так, а не что
ожидалось; тест читается как предложение; никакого разделяемого состояния —
каждый тест полностью автономен.

Организация тестов — по `RULE.md`: unit-тесты в `#[cfg(test)] mod tests`,
интеграционные в `tests/`, `proptest` для нетривиальных пространств входных
данных, реальная база вместо моков.

### Фикстуры

Передавать явные аргументы тестируемым типам, а не значения по умолчанию.
Пропускать нерелевантный код, побочные эффекты, аксессоры и ошибки. Предпочитать
фейки и стабы мокам. Использовать нерегулярные, случайные входные данные.
Инлайнить короткие фикстуры, объёмные генерировать в рантайме. Заводить
типы-фикстуры против дублирования, используя временные директории. Не мокать
файловую систему, сокеты и память.

### Рантайм

Отключать логирование в тестах. Ограничивать каждое ожидание таймаутом.
Тестировать конкурентность, повторяя нестабильные блоки. Считать, что интернета
нет; использовать эфемерные порты.

### Puzzle Driven Development

Нерешённые задачи оформлять как «пазлы» — `// TODO:`-комментарии или задачи в
`TASKS.md` — и откладывать на потом. Не решать побочные проблемы на месте:
зафиксировать пазл, описать контекст и продолжить основную задачу. Каждый пазл
содержит: что нужно сделать, почему это не сделано сейчас, и ссылку на задачу.
Пазлы позволяют держать изменения минимальными и сфокусированными, не теряя
обнаруженных проблем.

## Жизненный цикл задач

Единственный источник правды о задачах — `TASKS.md` в корне репозитория.

### Статусы

| Статус | Значение |
| --- | --- |
| `ОПИСАН` | Задача заведена и детально проработана: что делать и как. В работу не взята |
| `ВЗЯТ` | Задача взята в работу, изменения ведутся сейчас |
| `ПАУЗА` | Работа начата и приостановлена; в задаче зафиксировано, что уже сделано и что мешает продолжить |

Переходы: `ОПИСАН → ВЗЯТ → (ПАУЗА → ВЗЯТ)* → закрыта`.

### Заведение задачи

Задача всегда заводится со статусом `ОПИСАН`. До перевода в `ВЗЯТ` она должна
быть проработана детально: что именно нужно сделать, как, какие файлы
затрагиваются, как проверить результат. Задача без проработки в работу не берётся.

### Структура TASKS.md

- Живой список задач, отсортированный по приоритету взятия в работу: самые
  приоритетные — первыми.
- В начале файла — таблица со всеми задачами (номер, приоритет, статус, краткое
  описание).
- Ниже — по разделу на каждую задачу с детальным описанием.
- Порядок разделов совпадает с порядком строк в таблице.

### Проработка и реализация

Обычная задача доводится до работающего кода. Проработка — часть такой задачи, а
не её итог: приняв решение, надо сразу реализовать его и только потом закрывать.
Задача, у которой зафиксировано решение, но нет реализации, остаётся открытой.

**Задача, заведённая на проработку, — исключение.** Её результат — принятое
решение, и завершается она одним из двух:

1. **Задачей на реализацию** — заведённой тут же, со статусом `ОПИСАН`, с
   зафиксированными решениями, выбранными библиотеками и версиями.
2. **Отказом** — зафиксированным решением не делать, с обоснованием.

Проработочная задача не закрывается, пока не появилось одно из двух. Решение
записывается в `TODO.md`: задача после закрытия удаляется, требование остаётся.

Выделять реализацию в отдельную задачу из **обычной** задачи допустимо только
тогда, когда реализация блокирована незакрытой зависимостью. Причина
указывается явно, со ссылкой на блокирующую задачу.

### Закрытие задачи

Задача закрывается, когда её результат реализован и проверен. После этого:

1. Сделать коммит **без Co-Author**.
2. Выполнить push.
3. Полностью удалить задачу из `TASKS.md` — и строку таблицы, и раздел.

Номер задачи и краткое описание остаются только в сообщении коммита.

### Находки в процессе работы

Если в ходе выполнения задачи найден баг — завести новую задачу и выставить
приоритет. То же самое для замеченных улучшений, исправлений и оптимизаций:
не чинить на месте, а заводить задачу. Это прямое следствие Puzzle Driven
Development и правила «держать изменения минимальными».

### Поддержка CLAUDE.md

`CLAUDE.md` постоянно поддерживается в актуальном состоянии. В нём только
информация о проекте, ключевые точки и правила процесса. Правила написания кода
живут в `RULE.md`, состояние задач — в `TASKS.md`; дублировать их сюда нельзя.
Лимит — 500 строк.
