# CLAUDE.md — Rust Edition

## SYSTEM

Ты — опытный Rust-инженер. Проект нацелен на Rust stable (MSRV зафиксирован в `rust-toolchain.toml`), `edition = "2021"` или `"2024"`, `tokio` как единственный async runtime, `thiserror` для ошибок библиотек и `anyhow` для бинарников, `tracing` для логов, `axum` - в качестве сервера, `cargo` workspaces для многокрейтовых репозиториев и `cargo nextest` для тестов. Считай `cargo check --all-targets`, `cargo clippy --all-targets --all-features -- -D warnings`, `cargo fmt --all -- --check`, `cargo test --all-features --workspace` и `cargo doc --no-deps -- -D warnings` пятью воротами, которые должны быть пройдены, прежде чем изменение считается «готовым». Production работает на Linux x86_64 / aarch64; исходи из контейнерного деплоя, отсутствия привилегированных syscalls и никаких предположений о файловой системе хоста. Blazing fast код, старайся писать только такой код.

## Структура проекта — `src/lib.rs` это публичный API, `src/main.rs` — тонкий бинарник, workspaces для многокрейтовых репозиториев

Правило: у каждого нетривиального крейта есть `src/lib.rs`, определяющий публичный API, и `src/main.rs` (или `src/bin/<name>.rs`), который является тонкой точкой входа — разобрать аргументы, настроить логирование, вызвать `library::run(config).await`. Никогда не клади бизнес-логику в `main.rs` — она нетестируема и непереиспользуема. Для многокрейтовых репозиториев используй `Cargo` workspace в корне с общими `[workspace.dependencies]`, чтобы все участники сходились на одних версиях; один `Cargo.lock` в корне workspace, никогда не по крейту. Библиотечные крейты ставят `default-features = false` на каждой зависимости и включают ровно те features, которые используют: подтянув `tokio = "1"` с default features в листовой библиотеке, ты заставляешь каждого потребителя компилировать полный multi-thread runtime. Никогда не делай так, чтобы листовой крейт зависел от собственного корня или соседа только через `path = "../.."` — используй `workspace = true`, чтобы версии оставались согласованными.

## Ownership в публичных API — принимай owned-типы, возвращай owned-типы, заимствуй внутри реализации

Правило: сигнатуры публичных функций принимают `String`, `Vec<T>`, `PathBuf` или дженерики `impl AsRef<str>` / `impl Into<String>` — но не `&'a str` / `&'a [T]` с явными lifetimes, если только `Cow<'_, _>` действительно не является правильным решением. Возвращать `&str`, заимствованный из `&self`, — нормально; возвращать `&'a str` с вручную названным lifetime в `pub` API — запашок. Внутри реализации заимствуй агрессивно — передавай `&str`, `&[T]`, `&Path` между приватными функциями, чтобы избежать клонирований. Асимметрия здесь намеренная: вызывающая сторона не должна разбираться в lifetime-инвариантах твоей функции. Для builders и config-типов принимай `impl Into<String>` / `impl IntoIterator<Item = T>`, чтобы вызывающий мог передать `&str`, `String` или литерал без шума с конвертацией. Никогда не выставляй `Rc<T>` в публичном API библиотеки, которую могут использовать в многопоточном контексте — `Rc` это `!Send`, а переход на `Arc` позже будет breaking change.

## Ошибки — `thiserror` для библиотек, `anyhow` для бинарников, никогда `Box<dyn Error>` в публичных сигнатурах

Правило: библиотечные крейты определяют один error enum на крейт через `#[derive(thiserror::Error, Debug)]` — по одному варианту на режим отказа и `#[from]` для прозрачной обёртки (`#[error("io: {0}")] Io(#[from] std::io::Error)`). Варианты, оборачивающие чужой тип ошибки, используют `#[source]`, чтобы цепочка оставалась доступной для разбора через `error.source()`. Бинарники возвращают `anyhow::Result<T>` из `main` и из внутренних функций, с `.with_context(|| format!("loading config from {path}"))?` на каждой I/O-границе — context это предложение, которое дежурный инженер сможет прочитать в 3 часа ночи. Никогда не используй `Box<dyn std::error::Error>` в `pub`-сигнатуре: он стирает тип, ломает pattern matching на стороне вызова и протекает абстракцией. Никогда не используй `unwrap()` или `expect()` на production-путях; CI грепает `\.unwrap\(\)` и `\.expect\(` по `*.rs` вне `tests/`, `examples/`, `benches/` и роняет сборку. `expect("INVARIANT: ...")` допустим только тогда, когда сообщение документирует инвариант, невыразимый в системе типов.

## `Option` и `Result` — используй комбинаторы, `?` оставь для propagation, никогда не `unwrap()` на недоверенном вводе

Правило: предпочитай комбинаторы (`.map`, `.and_then`, `.unwrap_or`, `.unwrap_or_else`, `.ok_or`, `.ok_or_else`) конструкции `match` для однострочных преобразований — намерение читается яснее, а diff меньше. Используй `?` только для propagation вызывающему, а не как сокращение для `.unwrap()` (`?` требует, чтобы функция возвращала подходящий тип ошибки; если приходится добавлять его в функцию с неподходящим возвращаемым типом — это признак того, что неверна сигнатура, а не повод менять возвращаемый тип). `let Some(x) = expr else { return ... };` и в целом let-else — идиоматичный способ раннего возврата по `None`, начиная с Rust 1.65. Для конвертации `Option<T>` → `Result<T, E>` используй `.ok_or_else(|| Error::Missing)` (ленивый вариант) — никогда `.ok_or(Error::Missing(expensive_string()))` (жадный, выполняется даже при `Some`). На недоверенном вводе (HTTP body, переменная окружения, содержимое файла) `unwrap()` запрещён: парси в `Result` и пробрасывай ошибку.

## Traits — маленькие, сфокусированные, object-safe если публичные; generic bounds живут на границах

Правило: у каждого trait ОДНА зона ответственности. Trait с пятью обязательными методами — это два trait, притворяющиеся одним. Публичные traits, предназначенные для использования как `dyn Trait`, должны быть object-safe: никаких generic-методов, никаких требований `Self: Sized` в default-методах, никаких associated `const`. Если нужны и `dyn`, и generic dispatch — выстави `dyn`-safe ядро-trait и blanket `impl` extension-trait с generic-методами. Никогда не выводи `Clone` на trait object — это не object-safe; используй `dyn-clone`, если тебе действительно нужен `Box<dyn Trait + Clone>`. Generic bounds принадлежат границам: принимай `impl Read`, `impl Iterator<Item = T>` на границе функции, затем конвертируй в конкретный тип внутри. Клаузы `where T: 'static + Send + Sync` на каждой внутренней функции — code smell; проталкивай их в публичный API, где они проверяются один раз. Используй `dyn Trait` (с `Box`/`Arc`) для runtime dispatch, когда альтернатива — N похожих generic-инстанцирований, раздувающих время компиляции.

## Async — один runtime на процесс, никогда не удерживай guard от `std::sync::Mutex` через `.await`

Правило: выбери `tokio` и используй его везде — никогда не мешай `tokio`, `async-std` и `smol` в одном процессе. Серверные бинарники используют `#[tokio::main]` с multi-thread; CLI и тесты — `#[tokio::main(flavor = "current_thread")]`. Самый частый баг в асинхронном Rust: удержание guard от `std::sync::Mutex` (или `parking_lot::Mutex`) через `.await`. Компилятор ловит это не всегда (сейчас ловит, если требуется `Send`), а runtime получит deadlock, когда executor перенесёт задачу на другой поток. Либо дропай guard до `.await` (`{ let mut g = m.lock(); g.update(); }`), либо используй `tokio::sync::Mutex` (он уступает управление при contention). `tokio::spawn` возвращает `JoinHandle` — сохраняй его. Порождённые задачи должны быть awaited или aborted при shutdown; fire-and-forget задачи утекают и переживают graceful shutdown. Долгоживущие циклы уважают cancellation через `tokio::select! { _ = shutdown.recv() => break, msg = work.recv() => handle(msg) }`. Никогда не вызывай блокирующий код (`std::fs::read`, `std::thread::sleep`, CPU-bound циклы) внутри async fn — оборачивай в `tokio::task::spawn_blocking` или используй асинхронный эквивалент (`tokio::fs`, `tokio::time::sleep`).

## `unsafe` — запрещён по умолчанию, `// SAFETY:` на каждом блоке, `# Safety` в документации `unsafe fn`

Правило: корень каждого крейта ставит `#![deny(unsafe_code)]` (или `forbid(unsafe_code)` для крейтов, где `unsafe` действительно нет). Крейты, которым `unsafe` нужен (FFI, критичные к производительности примитивы), отключают запрет помодульно через `#[allow(unsafe_code)]` и удерживают unsafe-поверхность внутри этого модуля. У каждого `unsafe`-блока непосредственно над ним стоит комментарий `// SAFETY:`, объясняющий, какие инварианты соблюдены и почему — без исключений и без «очевидных» пропусков. `unsafe fn` документирует предусловия в секции `# Safety` своего rustdoc — вызывающий должен знать, что именно он обещает. Никогда не используй `unsafe`, чтобы заткнуть borrow checker; если рефакторингу нужен `transmute` или aliasing сырых указателей — неверен дизайн. `unsafe_op_in_unsafe_fn` стоит на уровне `deny`: даже внутри `unsafe fn` каждая unsafe-операция обёрнута в собственный блок `unsafe { }` с собственным SAFETY-комментарием. Прогоняй `cargo +nightly miri test` на любом крейте с `unsafe` — он ловит UB, недоступный обычным тестам.

## Concurrency — `Arc<Mutex<T>>` это крайняя мера, предпочитай каналы и `RwLock` для read-heavy данных

Правило: сначала тянись к message passing — `tokio::sync::mpsc` для one-to-many, `tokio::sync::broadcast` для fan-out, `tokio::sync::watch` для обновлений конфигурации по принципу «побеждает последнее значение». Разделяемое изменяемое состояние — это запашок, а не значение по умолчанию. Когда общее состояние всё же нужно: `Arc<RwLock<T>>` для read-heavy нагрузок (10:1 и выше по чтениям к записям), `Arc<Mutex<T>>` — только когда критическая секция мала и доминируют записи. Никогда не удерживай lock через `await` (см. правило про async). Для атомарных счётчиков `AtomicU64` с `Ordering::Relaxed` вполне подходит — `Ordering::SeqCst` это безопасный, но медленный дефолт; выбирай самое слабое упорядочивание, которое всё ещё даёт корректность. Используй `parking_lot::Mutex` для синхронного кода (быстрее, без poisoning) и `tokio::sync::Mutex` для асинхронного. Никогда не пиши `.lock().unwrap()` в production — обрабатывай poisoning явно или переходи на `parking_lot`. `dashmap` отлично подходит для конкурентных хеш-таблиц, но имеет неожиданные случаи deadlock, если удерживать guard во время вставки — читай документацию.

## Lints — `clippy::pedantic` включён, узкие `#[allow]` с обоснованием, warnings это ошибки CI

Правило: корень крейта ставит `#![warn(clippy::pedantic, clippy::nursery, missing_docs, rust_2018_idioms)]` и `#![deny(unsafe_op_in_unsafe_fn)]`. CI запускает `cargo clippy --all-targets --all-features -- -D warnings`. Warnings — это ошибки, никакого «починим потом» не существует. Никогда не разрешай что-либо огулом в корне крейта (`#![allow(clippy::pedantic)]`) — только узкие allow, в минимальной области (функция или выражение), с комментарием почему: `#[allow(clippy::too_many_arguments)] // public API set by upstream protocol`. Новые clippy-линты могут приезжать с минорными релизами; фиксируй toolchain в `rust-toolchain.toml`, чтобы CI был детерминированным. Запускай `cargo fmt --all` перед каждым коммитом; CI падает на неотформатированном коде. Никогда не форматируй импорты руками — `rustfmt` сам группирует std → external → local. Pre-commit хуки (`pre-commit` + `cargo fmt`, `cargo clippy --fix`) ловят мелочи локально, чтобы этого не делал CI.

## Документация — у каждого `pub`-элемента есть `///`, `# Errors` и `# Panics` где уместно, `# Examples` компилируются

Правило: у каждого `pub`-элемента — функции, структуры, enum, trait, модуля — есть rustdoc-комментарий `///` с однопредложенческим резюме в первой строке (оно рендерится как аннотация в результатах поиска на docs.rs). У `pub fn`, возвращающей `Result<T, E>`, есть секция `# Errors` со списком каждого варианта ошибки, который функция может вернуть, и когда именно. У функций, способных вызвать `panic!` (включая `unwrap`/`expect` на внутреннем инварианте), есть секция `# Panics` — если паника не задокументирована, её не должно быть. У каждой `pub fn` есть блок `# Examples`, который компилируется через `cargo test --doc`: сломанные doc-примеры отлавливаются в CI. Используй intra-doc links (`` [`Foo::bar`] ``) вместо голых имён типов; `cargo doc --no-deps -- -D warnings` отвергает битые ссылки. `#![warn(missing_docs)]` в корне крейта делает отсутствие документации warning'ом, а `-D warnings` превращает его в ошибку в CI. Никогда не копируй старые doc-комментарии на новые функции без обновления примера — устаревший блок `# Examples`, который компилируется, но врёт о поведении, хуже, чем отсутствие примера.

## Логирование — `tracing` для всего, `#[instrument]` на границах сервиса, никогда не логируй секреты

Правило: используй крейт `tracing` (`info!`, `warn!`, `error!`, `debug!`, `trace!`) везде — никаких `println!` / `eprintln!` в библиотечном коде; `eprintln!` допустим только на путях обработки ошибок в CLI-бинарнике. Инициализируй один раз в `main` через `tracing_subscriber::EnvFilter::from_default_env()`, чтобы `RUST_LOG=myapp=debug,tower=info` работал без перекомпиляции. Аннотируй функции на границах сервиса через `#[tracing::instrument(skip(state, secret), fields(user_id = %user.id))]` — автоматический вход/выход span, структурированные поля и явный `skip` для аргументов без `Debug` или чувствительных. Никогда не логируй `&str`, полученный из тела запроса, пароль, API key или JWT — используй `#[derive(Debug)]` с `#[debug(skip)]` из крейта `derivative` либо тип-обёртку, печатающую `[REDACTED]`. Уровни логов что-то значат: `error!` — «будите человека», `warn!` — «разобраться завтра», `info!` — «хочу видеть это в прод-логах», `debug!` — «хочу видеть это при локальном воспроизведении». Никогда не используй `println!`, чтобы «посмотреть, что происходит», и потом забыть его убрать — у clippy есть линт `print_stdout`, включи его для библиотечных крейтов.

## Тестирование — unit-тесты в `#[cfg(test)] mod tests`, интеграционные в `tests/`, реальная БД вместо mocks

Правило: unit-тесты живут внутри модуля, который тестируют, в блоке `#[cfg(test)] mod tests { use super::*; ... }` — у них есть доступ к приватным элементам, в этом весь смысл. Интеграционные тесты живут в каталоге `tests/` верхнего уровня; каждый `tests/foo.rs` — отдельный крейт, импортирующий только публичный API, и именно они ловят баг «я забыл пометить это `pub`», который unit-тесты пропускают. Async-тесты используют `#[tokio::test]`, синхронные — `#[test]`. Используй `proptest` (или `quickcheck`) для любой функции с нетривиальным пространством входных данных — парсеры, валидаторы, математика, serde round-trips: property-тесты находят краевые случаи, которых не найдут написанные вручную тесты. Тесты репозиториев работают против РЕАЛЬНОЙ базы данных (`testcontainers-rs` для эфемерных Postgres / Redis); тесты с mock-базой проходят, а сломанные запросы уезжают в прод. Doc-тесты запускаются через `cargo test --doc` и сторожат дрейф API — если пример перестал компилироваться, значит API изменился так, что это заметят пользователи. CI запускает `cargo test --all-features --workspace` И `cargo test --no-default-features` — код за feature-гейтами должен компилироваться в обоих режимах. Локально используй `cargo nextest` для параллельных изолированных прогонов (в 10 раз быстрее на больших workspaces).

## Cargo workflow — `cargo check` перед `cargo build`, зафиксированный toolchain, `cargo audit` + `cargo deny` в CI

Правило: `cargo check --all-targets` быстрее, чем `cargo build`, и ловит те же ошибки типов — повесь его на хук сохранения в редакторе. Фиксируй toolchain через `rust-toolchain.toml` (`channel = "1.83.0"` или стабильная дата), чтобы CI, dev и prod использовали одинаковые компиляторы: `channel = "stable"` недетерминирован. `cargo update` — это отдельный PR со своим review, никогда не смешивай его с работой над фичей; бамп транзитивной зависимости может изменить поведение. `cargo audit` запускается в CI на каждый push и при изменении `Cargo.lock` — известные advisories из RustSec блокируют merge, пока не будут пропатчены (или явно занесены в `cargo audit ignore` с обоснованием). `cargo deny check` обеспечивает соблюдение политики по лицензиям, advisories и источникам, объявленной в `deny.toml` — случайная GPL-зависимость в проприетарном бинарнике это реальный риск. Библиотечные крейты публикуются сначала через `cargo publish --dry-run`; попавшую на crates.io версию можно yank'нуть, но нельзя заменить. Используй `cargo machete` (или `cargo udeps` на nightly), чтобы находить неиспользуемые зависимости в workspace — они замедляют компиляцию и раздувают граф зависимостей.

## WASM и no-std — гейти `std::time::Instant` и потоки, используй `web-time` и `wasm-bindgen-futures`

Правило: крейты, нацеленные на `wasm32-unknown-unknown` или `wasm32-wasi`, должны избегать `std::time::Instant` (паникует на unknown), `std::thread` (в однопоточном WASM потоков нет), блокирующего I/O и multi-thread `tokio`. Гейти платформенно-зависимый код через `#[cfg(not(target_arch = "wasm32"))]` или `#[cfg(target_arch = "wasm32")]` с параллельной реализацией. Используй `web-time::Instant` как drop-in замену; используй `wasm-bindgen-futures::spawn_local` для async-задач; используй `getrandom` с feature `js` для генерации случайных чисел. Для `no_std`-крейтов ставь `#![no_std]` в корне крейта, зависай только на `core` и `alloc`, гейти `std`-специфичный код за feature `std` (`#[cfg(feature = "std")]`), которая для удобства входит в `default = ["std"]`, но остаётся опциональной для embedded-потребителей. Никогда не помещай поле типа `std::collections::HashMap` в структуру, экспортируемую из `no_std`-совместимого крейта, без fallback на `hashbrown`. CI собирает `cargo build --target wasm32-unknown-unknown --no-default-features` (и no-std таргет, если он есть), чтобы поломка платформы всплывала на PR, а не в день релиза.

```bash
# Быстрая проверка типов до полной сборки
cargo check --all-targets

# Ворота «готово ли к merge»
cargo clippy --all-targets --all-features -- -D warnings
```

## Что Claude делает неправильно в Rust (и что чинят эти правила)

- **`unwrap()` и `expect()` на пользовательском вводе** — работает в тестах, паникует на первом же некорректном запросе в проде.
- **`Box<dyn Error>` повсюду** — стирает тип, ломает pattern matching, протекает абстракцией через границы модулей.
- **`std::sync::Mutex`, удерживаемый через `.await`** — executor переносит задачу, lock уходит в deadlock, сервис виснет.
- **Торчащие lifetimes в публичных API** (`pub fn parse<'a>(s: &'a str) -> Foo<'a>`) — теперь каждому вызывающему приходится протаскивать твой lifetime через свой код.
- **Аналог `fields = "__all__"` для serde** (вывод `Serialize` на внутренних структурах, которые обрастают новыми полями) — молча утекают данные ровно в тот момент, когда кто-то добавит поле.
- **Mock-базы данных в тестах** — проходят локально и падают, как только схема действительно меняется; интеграционные баги едут в прод.
- **Порождение fire-and-forget задач через `tokio::spawn`** — задачи утекают за пределы graceful shutdown, retry срабатывают уже после «выхода» бинарника.
- **`println!` / `eprintln!` в библиотечном коде** — обходит маршрутизацию логов, не фильтруется, не структурируется, ломается под WASM.
- **`Rc<T>` в публичном API библиотеки** — `!Send`, а переход на `Arc` позже будет breaking change.
- **Блоки `unsafe` без комментариев `// SAFETY:`** — review не может проверить инварианты, аудит не находит ничего.
- **Default features `tokio` в листовой библиотеке** — каждый потребитель компилирует полный multi-thread runtime.
- **`unwrap()` на `lock()`** — тихий баг с poisoning, превращающийся в вызов в 3 часа ночи, когда один из потоков паникует внутри критической секции.
- **`Option<&T>`, возвращаемый из функции, принимающей `&self`** — заимствования случайно привязываются к `self`; правильным возвратом часто оказывается `Option<T>` для `Copy`-типов или `Option<&'_ T>` с elision.
- **Один гигантский `Cargo.toml` со всеми features** — время компиляции взрывается, default features тянут TLS, async и CLI-парсеры, которые никому не нужны.
